## 1. 모델 호출 수와 입력 경로

**단순 대기·수치 제어에 별도 판단 호출을 쓰지 않는 방식**을 우선 비교합니다. E14는 모델의 움직임 뒤 고정 중립 시간을 제어기가 추가합니다. 다음 관측·판단이 필요한 접촉 보정을 긴 목록으로 무조건 묶지는 않습니다. 장기 후보는 VLM이 단계·대상을 정하고 작은 시각 제어기가 제한된 보정을 수행하는 구조입니다. 입력 축약만으로 큰 가속을 약속할 수는 없습니다. [OpenAI 호출 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization) · [캐시 조건](https://developers.openai.com/api/docs/guides/prompt-caching)

사용자는 기술적인 실행 속도 개선을 요청했으므로, 속도 서비스 등급 변경을 이번 최적화에 포함하지 않습니다. 해당 후보는 중단했고 실제 설정 변경·비교 호출은 없었습니다. 현재 `gpt-6-astra/ultra`와 검증된 exec 경로를 유지합니다. 상주 App Server는 앞선 실제 호환성 실패가 있어, 프로세스 시작 시간을 분리하지 않은 채 상주화가 큰 효과를 낸다고 주장하지 않습니다.

E14의 고정 정착은 추가 관측 판단 없이 정해진 중립만 수행하는 작은 첫 비교입니다. 이후 공개 관절 잔차·속도에 따른 제한된 완료 확인, 관측 기반 작은 보정, 불확실성이 커질 때 새 Astra 판단을 요청하는 구조를 검토합니다. 모델 호출이 줄어도 물리 진행이 늘 수 있으므로 전체 경과와 실제 과제 결과를 함께 비교합니다.

## 2. 시뮬레이터의 카메라와 물리 비용을 나누기

현재 [sensor capture](../../../src/PhyRC_Sim/Policy/sensors.py)는 `world.render()`와 Replicator의`rt_subframes=4,delta_time=0,wait_for_render=True`를 사용합니다. 소스는 오래된 카메라 프레임을 피하기 위한 대기를 명시합니다. E15에서 capture 전체 시간을 측정했으나 내부의 render·Replicator·readback은 아직 분리하지 않았으므로 불필요한 중복이라고 결론내리지 않습니다.

기본OFF인 v1 수치 타이머를 [step_profile.py](../../../participant/collection/step_profile.py)에 구현해 **capture,그 외 observe,그 외 step**을 구분했고 E15에 적용했습니다. 추가 렌더·GPU 동기화·물리 진행 없이 기존 호출을 감싸고, 결과는 신뢰된 계측 기록에만 남깁니다. 이후 카메라가 지배적일 때 render·Replicator 대기·readback을 더 나눕니다. 물리240Hz·내부 로봇 제어60Hz·정책/관측20Hz·5개 RGB-D 관측·평가 정의는 유지합니다.

작은 후보로는 같은 정지된 capture 내부에서 로봇별 link transform 읽기를 재사용하는 방법이 있습니다. 현재 wrist/head를 각각 읽어 두 로봇에4회 전체 transform을 요청합니다. 효과는 측정 전이며 다른 시각의 데이터를 재사용하지 않습니다.

## 3. 저장·전송은 다음 순위

E13의 collector 내부 요청 실행 합계656.139초와 외부 dispatch702.869초 사이에는46.730초가 있습니다.66요청 평균0.708초이며, JSON 변환·pipe·클라이언트 해석 등이 포함될 수 있지만 전부 직렬화 비용으로 확정하지 않습니다. 공개5RGB-D 배열의 중첩 JSON 전송은 분리 계측 후 비교할 후보입니다.

Writer는 전이마다 양쪽 관측 저장·LZF 압축·flush를 수행합니다. 저장 비용을 전부 없애더라도 전체 시간 절감 상한은 이 실측에서 약2.1%이므로, 내구성을 낮추는 flush 변경보다 환경 내부 계측을 먼저 합니다. Chrome/WebRTC는 꺼져 있고 E13 idle render는0이므로 현재 브라우저를 더 끄는 데서 추가 이득을 기대하지 않습니다.
