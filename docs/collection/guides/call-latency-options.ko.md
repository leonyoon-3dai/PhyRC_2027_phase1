## 2. 5점 목표에 맞추면 달라지는 점

먼저 노리는 항목은 `pickup`입니다. 공식 조건은 같은 그리퍼로 잡은 부위를 잡았던 위치보다 5cm 이상 올리고 **시뮬레이션 시간 3초** 유지하는 것입니다. 단순 닫기 명령이나 로봇 팔 상승만으로 득점을 확정할 수 없습니다. [저장소에 보존한 공식 평가 정의](../../competition/EVALUATION.md)

현재 모델 대기 중에는 물리 시간이 정지합니다. 따라서 모델을 50초 기다려도 3초 유지 조건에는 기여하지 않습니다. 3초를 진행하려면 20Hz 기준 최소 60 step이 필요합니다. 동일한 최대 20 step 계약을 유지해도, 한 계획 안에서 짧은 유지 구간을 세 번 이상 실행하는 설계는 가능합니다. 실제로 옷이 유지되는지 공개 관측으로 점검해야 합니다.

5점이 채워졌는지 확인하는 공식 평가 감시기는 실행 종료만 담당합니다. 점수나 내부 파지 상태를 행동 모델 또는 로컬 제어기의 입력으로 넣지 않습니다.

## 3. 한 번의 호출로 여러 시도: 세 가지 다른 방식

| 방식 | 한 번에 받는 것 | 호출 절감 가능성 | 핵심 한계 |
|---|---|---|---|
| 고정 행동 목록 | 접근 → 닫기 → 들기 등의 여러 행동 | 간단한 반복에서 가능 | 중간 실패 이후에도 오래된 계획을 계속 실행할 수 있음 |
| 여러 파지 후보 | 위치·방향 후보 A/B/C | 후보를 독립적으로 실행·평가할 수 있을 때 가능 | 후보 선택과 실패 판정을 누가 수행할지 별도로 필요 |
| 조건부 계획 | 관측 조건, 행동, 분기, 재시도·시간 상한 | 계획 재사용과 여러 짧은 복구를 묶을 수 있음 | 공개 관측 기반 판정기와 제한된 실행기를 새로 구현·검증해야 함 |

**권장 설계는 조건부 계획과 로컬 피드백의 조합**입니다. Astra가 접근·파지·복구 전략을 정하고, 서버의 작은 제어기가 새 공개 관측을 보며 짧은 행동을 실행합니다. 계획을 벗어나거나 판단이 불확실하면 정지하고 Astra를 다시 호출합니다. 공식 지연 가이드도 순차 요청의 결합과 일반 코드로 처리 가능한 작업의 분리를 제안합니다. [OpenAI 지연 최적화](https://developers.openai.com/api/docs/guides/latency-optimization)

아래는 동작 설명용 의사코드이며 현재 사용할 수 있는 API가 아닙니다. 최초 시도 포함 최대 3회라는 수치도 검토용입니다.

```text
Astra 호출 1회 → 파지 후보·짧은 행동·복구 분기·예산을 포함한 계획

전체 후보를 통틀어, 최초 시도 포함 최대 3회:
  공개 RGB-D와 로봇 상태로 접근·정렬
  제한된 닫기 → 작은 시험 들기
  새 공개 관측으로 옷이 그리퍼를 따라 움직이는지 확인
  판단이 불확실하거나 시야를 잃으면 정지 → Astra 재호출
  실패가 명확하면 짧게 복구 → 다음 후보
  유지가 확인되면 짧은 유지 구간을 반복하며 계속 관찰
  시간·행동 예산을 소진하면 정지 → Astra 재호출

별도 신뢰된 감시기: 공식 누적 5점 이상 → 종료·사용자 리뷰
```

파지 확인은 닫기 명령을 그대로 성공으로 바꾸는 규칙이 아닙니다. 옷과 손목의 상대 이동, 높이 변화, 가려짐을 공개 센서에서 추정해야 합니다. 임계값·신뢰도와 실수 유형을 먼저 검수해야 하며, 구현되지 않은 판정기를 이미 동작하는 것처럼 취급하지 않습니다. 매 제어 구간의 `(2,9)` 행동·관측·다음 관측·시간을 기존 20Hz 자료로 보존합니다.

Code as Policies는 지각 결과와 제어 함수를 조합한 조건문·반복문 정책을 제시합니다. 계층적 코드 생성 자체는 추가 모델 호출을 사용할 수 있으므로 논문의 전체 실행이 항상 한 번의 호출이라는 뜻은 아닙니다. VoxPoser는 생성된 코드를 재사용하고 새 시각 피드백으로 다시 계산하는 방법을 설명합니다. 이를 우리 과제의 제한된 계획 실행기에 참고할 수 있지만, 두 연구가 PhyRC의 변형 의복 파지를 해결했다는 근거는 아닙니다. [Code as Policies](https://code-as-policies.github.io/), [VoxPoser](https://voxposer.github.io/)

### 상주 프로세스는 무엇이 다른가

상주 컨테이너에서 `docker exec`만 반복하면 CLI 재시작은 남습니다. Codex App Server는 초기화와 thread 연결 뒤 여러 `turn/start`를 처리할 수 있어 프로세스 유지의 후보입니다. stdio 연결이면 새로운 외부 포트가 필요 없습니다. 다만 현재 격리·도구 거부·타임아웃·오류 후 폐기·세션 재개를 다시 검증해야 합니다. 시작 비용의 실측 분해가 없으므로 이것만으로 수십 초를 줄인다고 주장하지 않습니다. [Codex App Server 공식 문서](https://learn.chatgpt.com/docs/app-server)

### 캐시와 관측 요약은 이미 있는 부분부터 구분

현재는 명시적 thread 재개와 턴별 고정 이미지 경로를 사용하며, 실제 사용량에 캐시 입력이 기록됩니다. 고정 지침을 앞에 두고 변화하는 관측을 뒤에 붙이는 구성을 검토할 수 있습니다. 캐시가 작동해도 새 이미지 해석과 추론·출력 생성은 남고, 세션 재개가 매번 캐시 적중을 보장하지는 않습니다. API의 캐시 옵션을 CLI 설정으로 그대로 적용할 수 있다고 가정하지 않습니다. [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)

이번에는 손목 접촉 판단 자체가 어려웠습니다. 이미지 수를 무조건 줄이기보다 원본을 보존하며 필요한 영역 강조, 공개 depth의 활용, 오래된 관측 요약을 각각 비교해야 합니다. 이들도 아직 적용하지 않았습니다.

### 최대 추론 설정과 속도 옵션

현재 정확한 표현은 **`gpt-6-astra`에 `ultra`를 요청하는 도구 제한 단일 actor**입니다. 공식 모델 안내는 Ultra의 병렬 subagent 활용을 설명하지만 현재 actor는 해당 기능과 도구 실행을 제한합니다. 따라서 Ultra의 병렬 실행 이점까지 사용 중이라고 할 수 없습니다. 그렇다고 내부 추론 effort가 자동으로 낮아졌다는 증거도 없습니다. [공식 모델 안내](https://learn.chatgpt.com/docs/models)

공식 Speed 문서는 Astra의 Fast와 Ultrafast를 안내합니다. 조사일 기준 Fast는 포함 사용량 2.5배·구매 크레딧 및 Enterprise 종량제 2배, Ultrafast는 각각 8배·6배이며 계정·요금제 조건이 있습니다. Ultrafast의 최대 8배는 토큰 생성 속도 설명으로 수집 전체가 8배 빨라진다는 보장이 아닙니다. 현재 계정의 자격은 확인하지 않았고 어떤 옵션도 변경하지 않았습니다. [공식 속도·사용량 안내](https://learn.chatgpt.com/docs/agent-configuration/speed)

### 비동기 실행과 요청 배치의 한계

측정 구간의 모든 호출·실행을 완벽히 겹친다는 이상적인 계산에서도 합계는 `503.41 + 134.38`에서 `max(503.41, 134.38)`초로 줄어드는 수준입니다. 약 21.1% 단축의 상한 예시이며 실제 관측 의존성과 초기·마지막 구간 때문에 달성하기 어렵습니다. 현재 1 simulation초 행동의 평균 환경 비용 약 22초로 평균 호출 50초를 전부 가릴 수도 없습니다.

Real-Time Chunking은 실행 중 다음 행동을 준비하면서 이어질 행동의 일관성을 다루는 연구입니다. 대상은 diffusion/flow VLA이며 현재 CLI JSON 정책에 바로 연결하는 옵션은 아닙니다. 오래된 관측과 행동 불연속을 해결해야 한다는 설계 근거로 참고합니다. [RTC 논문](https://www.physicalintelligence.company/download/real_time_chunking.pdf)

OpenAI Batch API는 24시간 이내 완료하는 비동기 대량 작업용이므로 다음 행동이 필요한 실시간 수집의 해법으로 적합하지 않습니다. 나중에 독립된 자료의 사후 분석에는 별도 검토할 수 있습니다. 응답 streaming도 사용자에게 글을 먼저 보여 주는 효과와 완성·검증된 행동을 얻는 시간을 구분해야 합니다. 미완성 JSON을 실행하지 않습니다. [Batch API](https://developers.openai.com/api/docs/guides/batch), [지연 최적화 가이드](https://developers.openai.com/api/docs/guides/latency-optimization)

## 5. 먼저 바로잡아야 할 계측 해석

조사 중 CLI 0.166.0의 `turn.completed.usage`가 thread 누적값인데 client가 각 호출 값을 다시 합산하는 문제를 확인했습니다. 원본을 보존하고 정정값을 별도로 기록합니다. 기존 `actor_usage` 합계로 토큰 비용이나 캐시 효율을 계산하지 않습니다. 시간 계측과 점수 판정은 별도이며 이 문제로 바뀌지 않습니다.

wiring r5의 입력 토큰은 기존 합산 133,146과 달리 마지막 완료 이벤트의 누계 74,558입니다. 출력은 719와 달리 330입니다. 실패·중단 호출까지 포함한 전체 청구 사용량과 동일하다고 단정하지 않습니다. 캐시 입력은 입력 토큰의 부분집합입니다. 이후 수정에서는 thread별 기준값·차분·중복·실패 이벤트를 처리해야 하며, 이번에는 수집 코드 변경 없이 이 사실을 기록합니다.

`actor_call_wall_s`에는 staging·Docker·CLI·네트워크·서비스 대기·추론·결과 처리가 섞여 있습니다. 모델 내부 시간이 제공되지 않은 상황에서 79% 전체를 순수 추론이라고 부르지 않습니다. 성능 실험에 앞서 시작·입력 준비·첫 응답·완료·환경 시간을 나누어 기록하는 것이 필요합니다.

## 6. 피드백 후 권장 비교 순서

1. **기준 자료 검수:** 이번 0점 과정의 접근·파지 가설·복구·종료를 보존하고 사용량 정정을 연결합니다. 실패를 삭제하거나 성공 시연으로 이름 붙이지 않습니다.
2. **최소 변경 비교:** 동일 Astra·effort·공개 입력을 유지하며 시작 비용을 분해합니다. 상주 구조가 줄일 수 있는 비용을 먼저 확인합니다.
3. **한 단계의 제한된 계획:** 우선 접근 또는 유지처럼 판정이 단순한 단계에서 짧은 행동 여러 개를 실행합니다. 접촉 구간은 관측 주기를 짧게 두고 불확실할 때 재호출합니다.
4. **최대 2~3회 조건부 시도:** 공개 센서 판정이 검증된 후 파지 후보·복구·재시도 상한을 추가합니다. 모델 effort·카메라 구성까지 동시에 바꾸지 않습니다.
5. **첫 공식 5점에서 종료·리뷰:** 기술 검수, 이미지·영상, 단계별 시간, 호출 수, 재시도와 공식 점수를 함께 확인한 뒤 추가 진행을 결정합니다.

현재 방식과 제안 방식을 비교할 때 같은 시작 배치 그룹과 동일한 wall·simulation·행동 예산을 사용합니다. 시작 상태를 재현하는 평가 정보는 actor에 제공하지 않습니다. 여러 시작 배치에서 비교하되 정확한 물리 되감기나 재현 성공을 검증 없이 가정하지 않습니다.

주요 지표는 **5점까지의 실제 시간, 정해진 예산 내 5점 도달 여부, 모델 호출 수, 파지 시도·복구 수, 불확실성으로 중단한 횟수, 전체 기록의 검수 통과 여부**입니다. 정해진 예산 안에 실패한 시도도 함께 집계합니다. 한 시도만으로 성공률이나 평균 도달 시간을 주장하지 않습니다.

계산 예시로, 같은 환경 비용과 호출당 평균을 유지하면서 10호출을 3호출로 줄이면 `3 × 50.34 + 134.38 ≈ 285.40초`입니다. 기존 637.79초보다 약 55% 짧지만 **성능 예측이 아닌 가정 계산**입니다. 복잡한 계획의 생성 시간이 길어지거나 로컬 지각 비용·실패가 늘면 이 절감은 줄거나 사라집니다.

## 7. 과정 데이터에 추가할 항목 제안

기존 전이 기록 위에 `plan_id`, `plan_version`, `primitive_id`, `attempt_index`, `parent_attempt`, `branch_reason`, `observation_step`, `executed_steps`, `replan_reason`, `termination_reason`을 연결하는 방안을 제안합니다. 아직 schema를 변경하지 않았습니다.

한 모델 응답에서 세 번 시도했더라도 실제 관측·행동·재시도 경계는 각각 보존해야 합니다. 로컬 제어기가 수정한 행동과 Astra의 계획을 구분하고, 실행하지 않은 후보를 실제 action label로 저장하지 않습니다. 공식 점수·동시 획득·success·원인 미확인 종료는 검수 영역의 별도 라벨로 남깁니다. 이렇게 해야 후속 VLA baseline과 RL·world model 자료에서 계획, 실행, 결과를 혼동하지 않을 수 있습니다.
