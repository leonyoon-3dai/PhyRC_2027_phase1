# E02 · 상주 App Server 이미지 연결 시험

**상태: 호환성 검증 실패로 보류.** 2026-11-06에 별도 App Server 어댑터를 만들고 합성 이미지로 연결을 시험했습니다. r1~r5 모두 실패 기록으로 보존했습니다. 총 `turn/start` 요청 시도는 3회이며, 어댑터가 승인하여 반환한 응답은 **0개**입니다. 같은 프로세스·thread에서 이미지 2턴을 완료하는 목표는 통과하지 못했습니다.

## 목적과 실행 범위

기존 방식은 매 모델 턴마다 Docker의 Codex CLI `exec/resume`을 실행합니다. E02는 `codex app-server`의 stdio 연결을 유지하고, 명시적인 같은 thread에 여러 `turn/start`를 보내는 방식의 연결 가능성을 확인하려는 실험입니다. 속도 개선이나 로봇 조작 성능은 이번 시험의 검증 결과가 아닙니다.

- 모델·설정: `gpt-6-astra` / `ultra`, Codex CLI `0.166.0`, 호출당 timeout 120초.
- 인증: 기존 ChatGPT 로그인 인증의 전용 사본. API 키 방식으로 전환하지 않았습니다.
- 격리: 기존 `Actor`의 Docker 파일시스템·내부망·모델 접속 proxy·도구 기능 제한을 재사용했습니다. 호스트 저장소와 시뮬레이터 자료를 모델 컨테이너에 연결하지 않았습니다.
- 입력 계획: 64×64 단색 빨강 이미지 → 초록 이미지. 두 번째 턴에서 현재 색상, 첫 색상과 첫 턴의 임의 문자열을 함께 답하도록 구성했습니다. 문자열은 합성 기억 검사용 입력입니다.
- 실제 범위: 모든 실행이 첫 턴 완료 이전에 종료되어 **초록 이미지를 사용하는 두 번째 모델 호출은 실행하지 못했습니다.**
- 출력 처리: 턴별 JSON schema, 명시적 thread·turn·RPC 식별자, 완료 이벤트와 허용된 응답 종류를 검사합니다. 미지원 알림이나 도구 요청은 응답 승인으로 이어지지 않습니다.
- **로컬 GPU와 로봇 시뮬레이션은 실행하지 않았습니다.** 로봇 행동, 시연 전이, 공식 점수 자료를 생성한 시험이 아닙니다.

프로토콜은 [공식 App Server 문서](https://learn.chatgpt.com/docs/app-server)와 설치된 CLI `0.166.0`의 `generate-json-schema --experimental` 출력으로 확인했습니다. 구현은 [별도 실험 어댑터](../../../participant/collection/codex_app_actor.py), 검사는 [CPU 프로토콜 검사](../../../tests/test_codex_app_actor.py)에 있습니다.

`모델 요청 시도`는 `turn/start`를 요청한 횟수입니다. 완료 응답 수나 청구된 추론 횟수로 해석하지 않습니다. r3~r5는 각각 첫 번째 턴을 요청했으나, 어댑터가 요구하는 정상 완료를 확인하지 못했습니다.

r5에서는 첫 번째 `agentMessage`의 완성된 JSON과 사용량 알림까지 수신했습니다. 해당 JSON의 빨강 판별·첫 색상·임의 문자열은 기대값과 일치했습니다. 그러나 `turn/completed` 확인 전에 읽음 상태 알림 처리에서 실패했으므로 **이를 승인된 응답이나 2턴 기억 검증 통과로 기록하지 않습니다.**

## 알림 처리에서 확인한 부족한 부분

실패 원인은 합성 이미지 분류 능력의 평가 결과가 아니라, 새 어댑터의 프로토콜 알림 분류가 충분하지 않았던 것입니다. 실제 수신 알림을 보면서 다음 검사를 좁게 추가했습니다.

1. r1 뒤에는 공식 문서에서 확인한 bundled bubblewrap 안내의 정확한 문구만 시작 단계에서 허용했습니다. 다른 설정 오류나 namespace 생성 실패를 일괄 허용하지 않았습니다. [공식 sandbox 전제 조건](https://learn.chatgpt.com/docs/sandboxing)
2. r2 뒤에는 공식 생성 스키마의 원격 제어 상태 중 `disabled`와 연결 환경 없음만 허용했습니다. 원격 제어를 활성화하지 않았습니다.
3. r3 뒤에는 기존 CLI에서 이미 구분하던 정확한 Code Mode 시작 안내를 동일 thread·`turn/started` 이전에만 허용했습니다.
4. r4 뒤에는 공식 생성 스키마의 moderation 진단 알림을 동일 thread·turn인지 검사한 뒤 별도 기록으로 처리했습니다. 차단 상태나 도구 관련 메타데이터는 거부합니다.
5. r5의 `ThreadReadStateChangedNotification`은 `threadId`와 `readState`를 갖는 thread 알림이며, 최상위 `turnId`가 없습니다. 이를 턴 알림으로 넘긴 분류가 남은 오류입니다. **r5 이후에는 코드 수정과 실제 모델 재시도를 중단했습니다.**

미지원 알림 전체를 무시하도록 바꾸지 않았습니다. 이 기록의 마지막 구현 상태는 실제 2턴 호환성이 검증되지 않은 실험 상태입니다.

## 도구·정리·보존 검증

- r1~r5의 **수신한 RPC 기록에서 도구 item과 서버 요청은 각각 모두 0개**였습니다. 이것은 모델에 등록된 도구의 총수가 0개라는 뜻은 아닙니다.
- 모든 실행의 인증 사본 삭제를 종료 후 별도로 확인했습니다. r3~r5의 결과 JSON에는 정리 완료가 기록되어 있습니다. r1~r2는 생성자에서 실패해 해당 결과 필드가 없지만, 별도 검증에서 사본 삭제를 확인했습니다.
- 마지막 확인 시 실험용 App Server·proxy 컨테이너는 남아 있지 않았습니다. 실패 이후 같은 actor 객체를 재사용하지 않았습니다.
- 입력 이미지·프롬프트·schema·실행 결과·개별 소스 사본·오류·수신 RPC를 실행별 경로에 보존했습니다. 실패 기록을 덮어쓰지 않고 새 실행 ID로 재시도했습니다.
- CPU 검사 9개, Python 문법 검사와 diff 검사를 통과했습니다. CPU 검사에는 합성 stdio 서버의 두 턴 유지·도구 거부·설정 불일치·timeout·EOF·schema 위반·실패 후 폐기가 포함됩니다. **실제 App Server의 두 턴 검증을 대신하지 않습니다.**

원본 위치는 `output/sessions/<run-id>/`와 `output/actors/<run-id>/runtime/`입니다. r5의 `verification.json`에는 다섯 실행의 종료 검증과 수신 로그 SHA256을 모았습니다. 이 경로들은 운영 환경의 로컬 보존 위치이며 GitHub 다운로드 링크가 아닙니다. 원본 RPC·모델 추론 이벤트·세션 식별자·인증·개인 접속 정보는 공개 문서에 싣지 않습니다.

## 판정과 다음 검증

E02는 **보류**입니다. 다음 작업은 `ThreadReadStateChangedNotification`을 thread 메타데이터로 정확히 분류하고 동일 thread 검사에 대한 CPU 회귀검사를 추가하는 것입니다. 이후 별도 실행 ID로 실제 빨강→초록 2턴, 같은 프로세스·thread 유지, 첫 입력 기억, 최종 JSON 승인, 도구 이벤트와 정상 정리를 모두 확인해야 합니다.

현재 기록의 짧은 실패 시간은 정상 모델 호출 속도를 나타내지 않습니다. **성공 모델의 지연 비교, 기존 로봇 수집보다 빨라졌다는 주장, 공식 5점 달성 자료로 사용할 수 없습니다.** 실제 2턴 호환성 검증 이후에야 같은 입력·모델·설정의 기존 CLI 방식과 비교할 수 있습니다.
