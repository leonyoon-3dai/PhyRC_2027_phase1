# 현재 RGB 픽셀의 공개 depth 조회: CPU 연결 검사와 향후 입력 후보

**종료된 E13의 공개 RGB-D에서 선택한 픽셀의 광축 Z와 카메라 XYZ를 정확히 조회하는 CPU 프로토타입을 확인했습니다. 현재 collector·actor에는 적용하지 않았습니다.** 의미 있는 손·입구·그리퍼 지점을 고르는 문제와 착의 성능은 해결하지 않았으며, 진행 중인 E15의 코드·입력도 바꾸지 않았습니다.

## 확인한 범위

기존 [B1 역투영 모듈](../../../participant/research/depth_backprojection.py)을 `patch_radius=0`으로 재사용했습니다. E13 `20261106-astra-hem-depth-001`의 저장 관측 `00000`, `00008`, `00009`에서 양쪽 손목 **6배열·48픽셀**을 원본 depth·유효 마스크와 대조했습니다. **유효 30개·무효 18개가 일치**했고 사용 원본의 SHA256은 변하지 않았습니다. 이 개수는 물체 검출 성공률이나 위치 정확도가 아닙니다.

별도 CPU 검사 **13개**는 Z/거리 구분, 정확한 원본 값, invalid·영상 경계·정수 좌표, 요청 예산, 오래된 관측 거부, 같은 카메라 내 차이와 교차 카메라·시각 거부, 응답 JSON 해석과 tool event 거부를 확인했습니다. 실제 파일 읽기·해시·조회 검사의 경과는 약 **0.055초**였습니다. 모델·GPU 호출은 없었고 HDF5·audit·평가·숨은 기하를 읽지 않았습니다. 이 offline 비용은 실제 모델 질의 지연을 포함하지 않습니다.

첫 관측의 [wrist0 RGB](../attempts/20261106-astra-hem-depth-001/first-call/01-robot_0_wrist.png)와 [wrist1 RGB](../attempts/20261106-astra-hem-depth-001/first-call/02-robot_1_wrist.png)는 수치 증거의 해당 원본 RGB SHA256과 일치합니다. 새 이미지나 수정 영상은 만들지 않았습니다. E13의 [당시 depth 패널 원본](../attempts/20261106-astra-hem-depth-001/first-call/15-current_wrist_depth.png)은 이미 전달된 입력입니다. [현재 표시용 재배치](../../gallery/assets/robot-layout-20261110/e13-current-wrist-depth.png)는 왼쪽robot_1·오른쪽robot_0으로 타일만 옮긴 파생 화면이며 당시 입력 원본을 바꾸지 않습니다. 여기서 제안한 픽셀별 숫자 질의는 이 문서 작성 당시 아직 전달하지 않은 별도 후보입니다.

## 숫자가 뜻하는 것과 뜻하지 않는 것

좌표는 원본 256×256 RGB의 0기준 `[u=열,v=행]`입니다. 현재 RGB와 같은 시각·카메라의 공개 depth를 그대로 읽으며, 패널·과거 사진·확대한 mosaic의 좌표를 사용하지 않습니다. `optical_z_m`은 **광축 Z의 미터 값**이고 카메라에서 표면까지의 유클리드 거리가 아닙니다. 선택적으로 공개 내부행렬 K로 `XYZ = Z × K⁻¹ × [u,v,1]ᵀ`, `range = ||XYZ||`를 계산합니다. 축은 X 오른쪽·Y 아래·Z 앞이며 world/base 변환은 사용하지 않습니다.

mask=false, 비유한 값 또는 Z≤0은 `null`입니다. 영상 밖 정수 좌표도 `out_of_bounds/null`로 남기며, 주변 값 대체·보간·가장자리로 좌표 이동을 하지 않습니다. 패널 표시 범위 0.03–1.20m로 수치를 자르지도 않습니다. invalid는 빈 공간의 증거가 아닙니다. 수식 왕복 검사는 calibration이나 RGB-depth 정합의 물리적 정확도 검증이 아닙니다.

상대 위치는 **동일 관측 ID·동일 시각·동일 카메라·동일 내부행렬의 유효 점**끼리만 뺍니다. 변환 없이 다른 카메라의 XYZ를 섞지 않습니다. 마지막 `00017`의 [robot_1_head 원본 RGB](../attempts/20261106-astra-hem-depth-001/images/final-robot_1_head.png)에서 depth를 보기 전에 고른 후보를 아래처럼 조회했습니다. 소수 표시는 반올림이며 전체 값은 수치 증거에 있습니다.

| RGB에서 고른 가시 표면 후보 | `[u,v]` | 광축 Z(m) | 손 표면 후보에서의 ΔXYZ(m) |
|---|---|---:|---|
| 손 표면 | `[83,125]` | 0.746409 | 기준점 |
| 회색 jaw 표면 | `[149,104]` | 0.621212 | `[0.255105, -0.069309, -0.125197]` |
| 아래쪽 노란 경계 | `[180,120]` | 0.831918 | `[0.420388, -0.024158, 0.085508]` |
| 위쪽 노란 경계 | `[196,96]` | 0.902540 | `[0.519473, -0.145742, 0.156131]` |
| 배경 검사점 | `[128,20]` | null | null |

**정확한 fingertip, hem/cuff/neck/fold, 가까운 테두리·먼 테두리의 의미는 미확인입니다.** 표의 차이는 선택한 가시 표면점 사이의 차이일 뿐, 가장 가까운 입구까지의 거리·통과 여유·접촉·손의 테두리 통과를 증명하지 않습니다. 향후에는 같은 손, 가까운 테두리, 먼 테두리, 손끝 후보를 구별하고 가려진 역할에는 억지 좌표를 채우지 않아야 합니다.

## 향후 요청 형식과 남은 검증

현재 action JSON과 구별할 요청 후보는 다음과 같습니다. 예시 좌표는 형식 설명이며 제어 정답이 아닙니다.

```json
{
  "kind": "depth_query",
  "observation_id": "<현재 관측을 식별하는 64자리 SHA256>",
  "camera": "robot_1_wrist",
  "pixels_uv": [[128, 128], [160, 128]],
  "include_camera_geometry": true
}
```

이 다섯 필드만 허용하는 구조입니다. 카메라는 현재 지정된 `overview`, `robot_0_wrist`, `robot_1_wrist`, `robot_0_head`, `robot_1_head` 중 하나이고, 요청당 1–8개 정수 좌표를 받습니다. bool·소수 좌표·추가 필드·오래된 관측 ID는 거부합니다. 형식상 좌표를 −4096…4096으로 제한하고, 실제 0…255 영상 밖은 `null` 처리합니다. 응답에는 원본 파일·요청·내부행렬 SHA, 공개 시각·카메라 순서, 각 점의 상태·Z와 선택적 XYZ/range를 기록합니다.

향후 controller가 **일반 도구를 열지 않고 final 응답 JSON을 분기**해, 같은 공개 관측에서 최대 1회·8점만 조회하는 방식을 검토할 수 있습니다. 조회 중 simulator 행동은 없고, 다음 모델 호출에 같은 시각의 수치를 전달한 뒤 행동 응답만 받는 후보입니다. 질의도 모델 호출·사용량·대기 시간에 포함하며 물리 전이와 구분해야 합니다. 현재 parser의 JSON 해석만 CPU로 확인했으며 **기존 행동 validator는 이 형식을 거부합니다.** 실제 CLI의 새 응답 schema·모델 동작·controller 통합은 미시험입니다.

**질의용 모델 왕복이 하나 늘어 전체 진행이 더 느려질 수 있습니다.** 속도 개선이나 호출 절감은 주장하지 않습니다. 기존 E13 결과도 [5/50·첫 소매 0](../attempts/20261106-astra-hem-depth-001/manifest.json)이며, 이 조회 후보의 제어·득점 개선 효과는 아직 측정하지 않았습니다.
